# Eco-Synthetic: Task Board

Cross-company task board. Owned by Eco; Assaf (OE) monitors usage.
Per constitution section 5: each agent writes to its own rows. Eco orchestrates.

Task schema (owner-required 2026-06-15):
| task_id | short_desc | status | detailed_desc | triggered_by | assigned_to | created | due | priority |

Status values: open, in-progress, blocked, done, cancelled.
Accountability rule: assigned_to agent owns the due date. Escalate to Eco (then owner) BEFORE the date slips. A silent miss is logged as a process miss.

### INTAKE checklist -- run BEFORE writing a new row (added 2026-08-02)

1. UNIQUE task_id. Grep the id in memory/board.md AND memory/board-archive.md before you write it.
   T-0046 was handed to two different tasks on 2026-07-27 by two parallel sessions; both collided
   entries reached company/decisions/decisions-log.md, which is append-only, so that collision is
   permanent and can never be corrected. Check first; it costs one grep.
2. assigned_to = EXACTLY ONE NAMED AGENT. Never a department ("R&D"), never a group, never a
   handoff string ("Ido (scope) -> R&D (build)"), never two names joined by "+". If the work truly
   has two legs, name the agent who owns it NOW and describe the other leg in detailed_desc.
   Ownership passes as a baton, it is never co-held.
3. A due date, OR the literal text "no due date because <reason>". "queued", "ongoing", "on-need",
   "next sprint" and "when slotted" are not due dates. If that is the honest state, say so in the
   "no due date because ..." form so the row cannot pretend to have a deadline it does not have.
4. EXACTLY 9 pipe-separated fields, and NO literal pipe character anywhere inside a cell. One stray
   pipe silently shifts every field after it, so a script reads the wrong owner and the wrong dates.
   Four rows (SHIR-001, SHIR-008, APS-017, CS-0001) parsed wrong this way until 2026-08-02.

### CLOSURE checklist -- run BEFORE setting status = done (added 2026-08-02)

1. Name the DELIVERABLE and its PATH, and confirm that file exists on disk in this session.
   "Delivered" with no path, or a path nobody opened, is not closure.
2. Symmetrically, before REACTIVATING a row, open the deliverable path FIRST. Four reactivation
   waves (AUD-010, AUD-011, AUD-013, T-0018) chased deliverables that already existed on disk,
   purely because nobody checked the file.
3. If a row is closing because it was wrong rather than because it was delivered, say FALSE ALARM
   or CANCELLED in plain words and record what the real state was (worked example: AUD-007).
4. Before recording ANY finding about a scheduled job (missed, overdue, failing), check
   integrations/runner/agent-prompts.md -- that file is the job registry of record. Run logs alone
   cannot tell "the job failed to fire" apart from "the job was deleted". AUD-007 escalated a
   retired job for six days on run-log evidence alone.
