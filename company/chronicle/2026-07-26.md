## [MISTAKE + PATTERN] Observability blackout corrected: 7 consecutive CRITICAL alerts were FALSE ALARMS

Date: 2026-07-26
Tag: mistake, pattern
Source: memory/wiki/cost-snapshots/2026-07-26.md

The "runner offline 22-26 days" CRITICAL alerts that fired every day from 2026-07-19
through 2026-07-25 (7 consecutive chronicle entries, 5 cost-snapshot ALERT files) were all
false. The runner has been active and healthy throughout.

Root cause: Assaf's cost-snapshot prompt read agent-runs.jsonl from the beginning (lines 1-300
of a 1600+ line append-only file). Those early lines are 2026-06-29 era entries -- the file's
oldest records. Reading from the top of an append-only log makes the log appear stale because
its oldest entries always look old. The tail is where the live activity lives.

The correction surfaced in the 2026-07-26 snapshot after the Assaf TAIL RULE fix landed
(integrations/runner/agent-prompts.md, delivered 2026-07-25 owner session, SHIR-007 commit
scope). Re-reading from offset ~1500 showed continuous runner health -- Rambo, Oracle, Ido,
Eco AM/PM, Assaf all firing on cadence with rc=0 throughout the "blackout" period.

Impact: no actual infrastructure outage occurred during the 7-alert window. The false alerts
caused ~7 stale ALERT files in memory/wiki/cost-snapshots/ and 7 false chronicle blackout
entries, but no decisions or deployments were blocked on bad data.

Lesson added to snapshot: ALWAYS read the END of append-only logs, not the beginning.
Pattern: monitoring that reads from offset 0 in a growing log is a latent false-alarm factory.
Any agent reading an append-only file for "current state" must read the tail.

## [MISTAKE + PATTERN] Eco CLI OAuth first unmasked error identified

Date: 2026-07-26
Tag: mistake, pattern
Source: memory/wiki/cost-snapshots/2026-07-26.md; memory/board.md SHIR-007 row

Following the runner.py stdout-fix (ECO-STDOUT-FIX, delivered 2026-07-25 in SHIR-007 commit
scope), the first unmasked error was captured on 2026-07-25 16:29Z:
"Failed to authenticate: OAuth session expired and could not be refreshed"

This is the Anthropic CLI's own session token (claude login), NOT the Gmail/Google OAuth. The
previous code path read only stderr; the claude CLI writes fatal auth errors to stdout with
empty stderr, so failures logged "rc=1: no stderr" and the real cause was discarded.

Pattern: Eco :57 first-of-cycle runs fail in ~9 seconds (too fast for any real work), later
jobs in the same cycle succeed. Consistent with an access-token refresh race after 2h idle --
the runner wakes the CLI, the Anthropic token has expired, the CLI tries to refresh, the
refresh fails on the first attempt, and the second invocation (a few minutes later in the
batch) succeeds with a fresh token.

Owner fix path (owner-only action): re-auth the CLI (claude login) OR set
CLAUDE_CODE_OAUTH_TOKEN to a long-lived token in the Task Scheduler job environment.
This diagnosis is a follow-up open from SHIR-007; Eco to surface to owner via dashboard.

Note: the same stdout-vs-stderr blindness was fixed in the bridge path on 2026-06-22 (SHIR-001)
but was never applied to the runner. The stdout-fix brings parity.
